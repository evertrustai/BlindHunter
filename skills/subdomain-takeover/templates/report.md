## Description

The subdomain `{{SUBDOMAIN}}` has a CNAME DNS record pointing to `{{CNAME_TARGET}}`, which is a {{SERVICE_PROVIDER}} resource that **no longer exists** or has been **deprovisioned**. 

Because the DNS record still exists but the underlying cloud resource has been removed, an attacker can register/claim the resource on {{SERVICE_PROVIDER}} and serve arbitrary content under the `{{SUBDOMAIN}}` domain. This is known as a **subdomain takeover** vulnerability.

## Impact

An attacker who claims the `{{CNAME_TARGET}}` resource on {{SERVICE_PROVIDER}} would gain full control of `{{SUBDOMAIN}}`. This enables:

1. **Phishing**: Host a convincing phishing page on a trusted subdomain of `{{TARGET_DOMAIN}}`
2. **Cookie Theft**: If cookies are scoped to `.{{TARGET_DOMAIN}}`, the attacker can read/write session cookies
3. **Cross-Site Scripting (XSS)**: Serve malicious JavaScript that executes in the context of `{{TARGET_DOMAIN}}`
4. **Content Injection**: Host malware or defacement content under a trusted domain
5. **Email Spoofing**: Potentially leverage the subdomain for SPF/DKIM bypass
6. **Brand/Reputation Damage**: Associate the organization's domain with malicious content

## Remediation

### Immediate Fix
**Remove the dangling CNAME record** from your DNS configuration:

```
# Delete the CNAME record for {{SUBDOMAIN}}
# In your DNS provider, remove:
# {{SUBDOMAIN}} → CNAME → {{CNAME_TARGET}}
```

### Long-term Recommendations
1. **DNS Hygiene**: Implement a process to remove DNS records when decommissioning cloud resources
2. **Automated Monitoring**: Set up periodic scanning for dangling DNS records
3. **Domain Verification**: Where possible, use services that require TXT record verification
4. **Inventory Management**: Maintain an inventory of all DNS records and their associated cloud resources
5. **Offboarding Checklist**: Always remove DNS records BEFORE deleting cloud resources
